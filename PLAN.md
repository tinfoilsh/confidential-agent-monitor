   Broadening what a sandbox may request does not let it apply changes or read

   paths and never enter proposal source, summaries or diffs.
5. Nov 3 14:15 decision: pending proposals are process-local memory only. They have

   Submission returns a receipt rather than holding the HTTP/SSH request open.
6. Bind review to the exact connection-scoped baseline: account configuration,
   default access, and every sandbox's access to that connection. Unrelated connection
   changes must not stale it. A change to the same connection requires a new review.
7. Nov 3 13:56 decision: normalize and automatically split a submitted batch by
   connection target. Connection setup plus its default/sandbox access stays together.
   Validate every group before storing all receipts in one submission transaction;
   each connection proposal is then approved independently.
8. Approval/rejection applies to the entire proposal. A small self-contained proposal
   may link from Activity to an inline review at the affected connection/agent/setting,
   similar to MCP review. Multi-resource proposals use a combined review page.
9. Activity shows proposer, reason, affected areas and a concise before/after summary
   or small diff. Preserve source TOML and effective diffs as a detailed fallback.
10. MCP tool-definition/pin review remains separate from configuration proposals.
11. Nov 3 13:41 pivot: creating generic connections and custom presets in the
    human owner UI saves directly. They show product warnings but do not enter the
    proposal flow. Proposals are the recommended automation/agent workflow.

## Existing path to reuse

- Agent client: `monitor policy propose FILE --reason ...`.
- Agent endpoint: `POST /policy/proposals` on `agent.monitor`.
- Existing input: TOML fragment plus optional deletions and required reason.
- Existing validation parses the fragment to `config.Change[]`, checks the agent's
  allowed proposal fields, prepares a candidate, and computes source/effective diffs.
- Existing UI renders the proposal as a `Change policy` Activity request.
- Existing approval detects policy conflicts and applies through `writeSettings`.
- Current limitations to replace: two-minute expiry, live waiting request, in-memory
  record, narrow `AgentChanges` proposal scope, and no structured owner submission.

## Backend checkpoint implemented (unstaged)

- Up to 32 pending proposals live only in the Monitor process; submission performs
  no state-bucket write and restart discards them.
- Owner API: submit/list/read/approve/reject at `/policy/proposals`.
- Agent API: submit returns only a pending receipt; it exposes no owner policy/diffs.
- Input supports exactly one TOML fragment (+ deletions) or structured `Change[]`.
- Proposals are immutable. Exact digest approval/rejection; replace by resubmitting.
- Normalize and split every submission by connection. Every split candidate passes
  normal config, connector and policy preparation before any proposal is stored.
- Stored owner review includes normalized connection changes, source diff and effective
  diff. Setup plus default/sandbox access for one connection remains one proposal.
- Credential leaf paths and nested credential values are rejected before preview or
  publication in memory.
- Staleness binds account configuration, resolved preset, default/effective sandbox
  access, relevant saved rules, and global inputs that affect connection behavior.
  Another connection can change without staling the proposal.
- Approval rebases reviewed changes over unrelated connection edits, revalidates, and
  atomically applies/consumes that connection proposal. Rejection consumes without apply.
  Approved/rejected outcomes (reason, proposer and diff) are appended to the existing
  encrypted S3-backed Activity/audit history. Approved policy persists normally;
  rejected proposal content is retained only in that decision audit.
- Agent proposal scope is widened only to the strict connection allowlist; the
  restricted agent _read_ view remains.
- Existing owner direct-write APIs and MCP definition review are unchanged.
- Client `monitor policy propose` now returns a pending receipt instead of waiting.

## Recommended caller flow

- **Trusted-device automation (preferred for local setup):** use the installed
  `monitor` client over the paired device's SSH identity to submit proposals. This
  gives device attribution and avoids routine access to the owner-panel session.
- **Sandbox automation:** use the same agent-side proposal endpoint under the
  sandbox's SSH identity.
- UI attribution uses **Trusted device `<name>`**, **Sandbox `<name>`**, or
  **Owner API**. An owner session is not falsely attributed to a trusted device.
- **Human owner UI:** save supported changes directly; generic/custom creation will
  show warnings but will not be forced through proposals.
- **Credentials:** configure through existing owner account settings/sign-in only.
- **Explicit owner-only or intentionally immediate work:** owner UI/API remains
  available when the owner requests it.
- `client/monitor` accepts `monitor policy propose --changes FILE --reason …`, so
  setup tools can submit their existing `Change[]` JSON. TOML fragments remain supported.
